# Desktop Application

[中文](zh-CN/DESKTOP.md)

The Tauri desktop application is a current-user control panel for the fixed-service `mtls-router`. It packages architecture-matching `mtls-router-manager` and `mtls-router` sidecars; it does not install either sidecar into `PATH` and does not provide certificate, upstream, or sidecar replacement controls.

> The checked-in CI and release workflows build six native desktop packages: Windows x86_64/arm64 NSIS installers, macOS Intel/Apple Silicon DMGs, and Linux x86_64/arm64 AppImages. Each package job runs inspection and an initialization-only startup smoke test on a matching target runner. Release signing is conditional on platform credentials, and macOS notarization/stapling additionally requires complete Apple notarization credentials; the per-target status file records the result. Inspection does not install or normally launch the package, so separate successful target-runner launch evidence remains required. See [Build and Release](BUILD.md).

## Install

Obtain the package for the operating system and CPU architecture from the trusted internal release channel. Do not move, replace, or run a sidecar separately from its desktop package.

- Windows: run the current-user installer matching x86_64 or arm64. Administrator elevation is not required by the application design.
- macOS: open the DMG matching Intel or Apple Silicon, then drag `CodeasierRouter.app` onto the Applications shortcut.
- Linux: make the matching x86_64 or arm64 AppImage executable and launch it as the current user.

If the operating system reports that the package is unsigned, unnotarized, damaged, or from an unknown publisher, stop and verify the release status with the distributor. Do not bypass platform security based only on the package filename.

The release asset set contains a `.sha256` file and a `signing-status-<os>-<arch>.txt` file for each desktop package. These prove the recorded checksum and signing/notarization result, not successful installation or launch. Obtain the separate target-platform launch evidence required by [Package verification](BUILD.md#package-verification).

## First launch

On first launch the application:

1. Verifies the packaged manager and router sidecars against the target architecture and build-time SHA-256 values, then checks the manager target, version, deployment ID, and management protocol.
2. Inspects `127.0.0.1:19099`.
3. Reuses a trusted, compatible router started by the CLI setup scripts, or starts the packaged router when the port is free.
4. Opens the Router page and checks process availability separately from upstream mTLS health.
5. Enables current-user launch-at-login by default. It can be disabled immediately in Settings without administrator privileges.

First launch never changes Claude Code, opencode, or Codex files. A second application launch activates the existing window instead of starting a second manager or router.

If either sidecar is missing, non-executable, altered, or for the wrong architecture, startup fails closed and reports that reinstallation is required. The application never downloads or replaces an individual sidecar. Reinstall the complete package from the trusted source, or use a valid whole-package desktop update when the installed application can still run it.

## Online updates

Stable desktop releases support whole-package online updates on Windows x86_64/arm64, macOS Intel/Apple Silicon, and Linux x86_64/arm64. The update replaces the desktop application together with its matched `mtls-router-manager` and `mtls-router` sidecars; it is not a sidecar-only update. This capability belongs only to the desktop application and does not add or change update behavior in the CLI binaries or setup scripts.

At startup the application silently checks `https://release.codeasier.top/latest.json` once. A failed check does not block startup. Settings shows the current and latest desktop versions, release notes when supplied, and a manual **Check for updates** action. Only a newer stable SemVer release is accepted; prerelease and build-metadata versions are not offered, and validation/non-stable builds are not published to the desktop update channel.

The application never downloads or installs an update without confirmation. After you approve the displayed stable version, it downloads the platform package, reports progress, verifies the mandatory Tauri updater signature, stops a verified desktop-owned router or a correlated legacy desktop router, installs the complete package, and restarts the application. If a correlated legacy router cannot be stopped with complete process identity, or correlated state remains stale, unknown, or unverifiable, the update is rejected. A compatible external router is not stopped. If installation fails after stopping a desktop-owned router, the application attempts to start that router again.

On every platform, online installation is supported only when the current package is running from an installation location and filesystem layout supported by that platform's Tauri updater. If the updater reports that the current location is unsupported or cannot replace the installed package, quit the application and manually install the complete new package from the trusted release channel; do not replace the packaged manager or router separately.

## Router ownership and state

The Router page distinguishes the local process from upstream health. A running process can therefore be healthy, degraded, or based on a health result older than 30 seconds. A still-running router left by an earlier desktop session or protocol generation is shown as a correlated legacy process. The current desktop may reclaim a compatible generation without stopping it; an incompatible generation is stopped and rebuilt only after an explicit Start action and complete router/previous-manager identity verification. Ordinary manager transport recovery never triggers that migration.
The Rust desktop runtime is the sole owner of `installation.json`. Its stable installation ID establishes current-installation lineage, while the stored sidecar hashes record the currently packaged binaries after their embedded hashes have been verified. They are not a historical hash allowlist and do not authorize protocol 1 or protocol 3 migration; legacy authorization remains limited to the supported protocol lineage plus complete router and previous-manager process identities.

- **Desktop router:** the application supervises a foreground child. Stop and Quit may stop it only after PID, start identity, executable identity, and ownership checks pass.
- **External router:** reuse is allowed only for a CLI setup-managed router whose recorded process identity, `deployment_id`, and `management_protocol_version` match the desktop build. A manually started process is not trusted from `/version` response shape alone.
- **Unknown port occupant:** the application never terminates it automatically and never switches to another port. Protocol v4 inspection returns a structured recovery action and stable reason: `force_terminate` for an eligible target, `manual_stop_required` for a service, insufficient privilege, or another user, and `unavailable` for a lifecycle-known protected process or unavailable identity. `insufficient_privilege` also covers terminate access denied by OS protection such as Windows PPL; an access-denied result does not reliably identify PPL. `protected_process` remains reserved for targets known to the application lifecycle. Only `force_terminate` includes a short-lived, single-use confirmation token. Complete identity is the default requirement: the manager verifies current-user ownership, process name, PID, start identity, complete executable path, and listener identity before the Router page offers **Force terminate occupant**. The confirmation shows the verified details and warns that termination is immediate and may lose unsaved data.
- **Windows PID-only exception:** Windows rejects a process as `different_user` when its SID is readable and differs from the desktop user; it never downgrades that known identity to PID-only. PID-only may be considered when the SID or the complete process identity cannot be read, but only if the TCP4 owner table identifies one unique PID for the exact `127.0.0.1:19099` listener, protected lifecycle targets are excluded, and a non-destructive `PROCESS_TERMINATE` access preflight succeeds. The panel shows only the PID and warns that identity, owner, start time, and executable remain unverified. Immediately before termination the manager repeats the exact-owner and protection checks and reacquires termination access; a disappeared, changed, duplicate, wildcard, malformed, ambiguous, or newly inaccessible target is refused without signaling. Unreadable lifecycle state and PID reuse remain residual risks. The application never requests elevation.
- **Supervised or blocked occupant:** a reliably identified Windows Service or Linux systemd user/system service is never force-terminated. The page displays bounded verified service/unit identifiers and fixed examples for `services.msc` / `sc.exe stop`, `systemctl --user stop`, or `sudo systemctl stop`. A copied Windows `sc.exe` command is safely quoted specifically for an Administrator **PowerShell** session; it is not a `cmd.exe` command. All examples are manual guidance only: the application neither executes commands nor requests administrator/root access. Insufficient-privilege and different-user processes likewise require manual action from the correct identity or privilege context; do not elevate the desktop application. On macOS the manager does not guess a launchd label, so an ordinary verified same-user process may remain forceable and later reoccupation receives generic Activity Monitor/`launchctl` guidance.
- **Termination and observation:** in verified-identity mode, manager success proves the confirmed process identity became absent and the port was observed released. In Windows PID-only mode, success proves the termination request succeeded and the original listener PID disappeared from that exact port; it does not independently prove that the process fully ended. Neither mode starts the router or promises lasting release. The desktop then periodically samples status for about 10 seconds. **The port remains released** means the sampled checks found the port released and detected no reoccupation; a sampled new occupant becomes **A service or watchdog reoccupied the port** and triggers a fresh inspection. Reoccupation between checks may go undetected. Starting the router cancels observation so the desktop-owned router is not misreported as reoccupation.
- **Manual fallback and errors:** if recovery is unavailable, guidance is unacceptable, or termination fails, identify and stop or reconfigure the listener with operating-system tools, then retry. Permission loss at confirmation, a failed termination request, and failure to prove timely release are reported separately as `OCCUPANT_PERMISSION_DENIED`, `OCCUPANT_TERMINATION_FAILED`, and `PORT_RELEASE_TIMEOUT`; none means that a replacement process was signaled.
- **Stale state:** a PID or executable mismatch is reported as stale and no signal is sent. Inspect the process and state before making a manual cleanup.
- **Degraded or stale health:** the router process may still accept local connections, but upstream service is not currently proven reachable. Use Retry health check and inspect Logs; do not treat stale health as healthy.

Each desktop-managed launch writes a separate log under the application data directory at `mtls-router-logs/YYYY-MM-DD/HH-MM-SS.log`. The Logs page follows the current or most recent launch, while **Open log location** exposes the grouped history for manual inspection.

See [Troubleshooting](TROUBLESHOOTING.md) for recovery steps.

## Tray, close, and quit

Closing the main window hides it in the system tray and leaves the router unchanged. On macOS the application also deactivates so the previously active app regains focus; the tray icon or a second launch reactivates and focuses the window. Use the tray icon to open the window, start or stop an eligible router, open logs, or quit.

Quit is different from closing the window. Quit stops a verified desktop-owned router and exits the application. It never stops a compatible external router or an unverified process. The regular Stop action remains unavailable for an unknown occupant, and the tray provides no force-termination action; occupant termination is available only through explicit confirmation on the Router page. Launch-at-login starts the desktop application on the next user login and applies the same discovery and ownership rules; it never terminates an occupant or blindly starts a second router. Closing the title bar still only hides the window and preserves an in-memory Agent draft. Leaving an Agent panel inside the application or using any interceptable quit path asks before discarding an unsaved draft; preview, write, and post-write reload operations cannot be left while active.

## Configure Agents

The Agents overview always presents Claude Code, OpenCode, and Codex in separate cards. Each card reports only configuration-file existence, writability, validity, configured state, and recovery eligibility. Detection is metadata-only, never returns the saved API-key value, and does not search for or depend on Agent CLI commands in `PATH`. It respects `CLAUDE_CONFIG_DIR`, `OPENCODE_CONFIG`, and `CODEX_HOME`.

Each supported Agent is always available for configuration management when its target path is writable. Each card opens a persistent panel for exactly that one Agent; the editor remains available after successful writes so the configuration can be maintained repeatedly. The desktop does not install, launch, or invoke Agent CLIs, and does not select or batch multiple Agents in one panel.

A card also offers **Clean up CodeasierRouter configuration** when `agent.detect` confirms a valid last-applied sidecar entry for that Agent and Agent writes are available. Cleanup is per Agent, not a bulk action. It does not use the router, model catalog, model flow, or global API key. If ownership is missing, invalid, or blocked by unresolved transaction recovery, automatic cleanup fails closed instead of guessing from configuration appearance; preserve the files and backups and handle the managed fields manually only after resolving transaction state.

Cleanup first presents a key-free review of exact managed path names, `replace` or `delete` file effects, planned backups and their sensitivity, and the last-applied sidecar change. It removes only ownership proven by the sidecar and current structure: Claude managed `env.*` keys; OpenCode `provider.mtls-router` and a root `model` still using the exact `mtls-router/` prefix when that root is owned; Codex `model_providers.mtls-router`, required managed model/auth-store roots, only optional roots represented by the saved Codex model config, and `auth.json` fields `auth_mode` and `OPENAI_API_KEY`. Other providers, settings, and auth metadata are preserved. Codex OS-keyring credentials are not deleted, and auth fields displaced by an earlier configuration write are not reconstructed.

Whole-file revision drift requires a separate confirmation, even when only an unrelated field changed. A recorded Agent target that is already absent is treated as cleaned and requires that confirmation; it receives no backup or mutation, while other targets and the sidecar continue through the transaction. Other target read errors still fail closed. The signed cleanup preview is revalidated before writing and before the journal; absent targets are checked before each mutation and again after the sidecar change immediately before commit. An absent target that reappears returns `PREVIEW_STALE`, rolls back prior changes, and retains sidecar ownership. Every affected existing Agent target and the manager sidecar are privately backed up and verified before mutation, then changed in one journaled transaction with the sidecar last. Every Agent-file backup is marked sensitive because preserved user fields may contain credentials; the manager sidecar backup is not sensitive. A present file is backed up and deleted when its semantic root is already empty or removing managed fields makes it empty; otherwise it is replaced with the preserved content. The final sidecar is deleted when its last Agent entry is removed. Rollback and startup recovery restore Agent files and sidecar together if the operation fails or is interrupted.

Cleanup removes the selected Agent file's managed authentication field, but it never deletes the global key in desktop `credentials.json` or any historical `*.bak-*` / `*.rollback-*` files. New cleanup backups are also retained after success and may contain API keys or other credentials. Protect and review them as sensitive recovery artifacts; remove them separately only when they are no longer needed.

Normal **Merge** preserves supported unrelated configuration. **Back up and rebuild** is a separate destructive recovery action shown only for eligible syntax-invalid files. It replaces the complete approved Agent file set with managed-only output; unrelated settings, comments, formatting, and valid companion-file metadata are lost. Its backups may contain API keys. Review this loss and protect every backup before continuing.

Agent configuration follows this single-Agent sequence:

1. Open a card. The panel always performs fresh `agent.detect`, reads only the credential summary, and then calls `agent.models` for that Agent when a key is present and the target is editable. Open **Merge** for a valid, writable Agent. For an invalid Agent, open **Back up and rebuild** only when detection marks it eligible; other invalid configurations must be repaired manually.
2. Rust loads the saved global API key managed on the API Keys page and discovers the manager's authenticated, build-filtered model catalog through the trusted local router for that Agent only. The overview does not load models or use the credential. If initial or full-reload discovery has no key, fails authentication, or cannot load the catalog, the panel remains open in a metadata-only state showing safe detection details and recovery actions; it does not expose field-level configuration. This boundary exists because render and preview require a catalog token issued by authenticated `agent.models` discovery. A failed background refresh instead preserves the existing draft and active flow, reports that external state could not be verified, and allows the operations that remain safe. The webview never receives the key.
3. By default, valid model IDs containing ASCII `/` are excluded; a release built with `SIMPLIFY=False` retains them. The filtered catalog is authoritative for the target Agent, imported config, preset, preview, and refresh. This is an immutable manager build policy, not a runtime preference or a restriction on proxy route support. The desktop never selects the first model, infers a choice from model names or capabilities, or substitutes a model. A visible build preset may supply an editable initial section only after the manager validates all of that section's exact IDs against this catalog.
4. Initialize the target Agent with `existing > preset > empty`, showing whether its section came from existing configuration or the recommended preset and listing missing base IDs for an unavailable complete preset section. Configure Agent-native choices: Claude primary/role inheritance plus optional display names and Standard/1M context, an OpenCode model subset/default/options, or one Codex model/options. Claude includes a localized **Enable Fable** control. Fable starts disabled for an empty Claude form; enabling it creates an inherit-primary selection and exposes the same inherit/explicit model, display-name, and Standard/1M controls, while disabling it removes the complete Fable selection and its metadata. Existing Claude wins over preset Claude as one complete section, so preset Fable is not merged into an existing Claude section that omits it. Preset values remain editable and imply no approval. Unset optional fields remain omitted. A key-free canonical model config can be imported or exported; import replaces the complete current form rather than merging with existing or preset values and preserves enabled or absent Fable through export, preview, and write.
5. Generate an exact structured preview and review redacted fragments plus every create, replace, preserve, migration, drift approval, state, and backup operation. Preview-normalized model configuration becomes the write input. Normal merge without explicit `OPENCODE_CONFIG` migrates canonical `~/.config/opencode/opencode.jsonc` to sibling `opencode.json`; an existing sibling is a migration collision. An explicit `.jsonc` override is normalized in place. Rebuild instead replaces its approved JSON or JSONC path in place as strict JSON and performs no sibling migration. Codex rebuild always replaces both `config.toml` and `auth.json`, creating a missing companion and discarding valid companion metadata; every existing file in that pair requires a backup.
6. Approve and write. Managed drift and Codex authentication changes still require explicit approval. Rebuild requires a separate destructive confirmation and must exactly match the one-Agent preview. Immediately before creating any write artifact, Rust reloads the saved global key and the manager refreshes the catalog. A successful transaction is reported immediately, then the panel reruns detection, credential summary, and model discovery to load the actual files into a new flow. Reload failure does not change the successful write result; retry performs the complete load again. The result can be dismissed without leaving the panel.

While an editable panel is open, a native window-focus event checks for external file changes at most once every 15 seconds. Manual refresh bypasses that interval, but all refreshes remain single-flight. A clean draft adopts a fresh configuration. An unsaved draft is never overwritten: unchanged external state preserves it, changed state requires choosing whether to keep it or load disk state, and an incompatible or newly unwritable target blocks editing until the draft is exported when its active flow remains valid, discarded, or safely recovered. Refresh does not poll and never rewrites an Agent file.

Import and export remain single-Agent, key-free canonical JSON operations, but both require a valid active model flow. Import replaces the current draft and invalidates any preview; export preserves draft, preview, and approval state. A conflict must be resolved before import. If a stale or expired flow cannot be rediscovered, the in-memory draft remains visible but catalog-validated export is unavailable until a valid flow is restored.

Rebuild eligibility requires at least one syntax-invalid file and no other blocker across the complete managed file set. Unsupported but valid structures, unreadable or oversized files, non-regular files, links, non-writable paths, unavailable parents, pending transaction recovery, and disabled writes are ineligible. Valid syntax and parser compatibility problems must be fixed rather than rebuilt. Rebuild applies only to the Agent whose card opened the workflow; there is no automatic recovery, parse bypass, global force overwrite, or fallback from merge failure to rebuild.

Rebuild output is deliberately managed-only: Claude `settings.json` contains only the managed `env`; opencode strict JSON contains only root `model` and `provider.mtls-router`; Codex `config.toml` contains only its managed model/provider settings and `auth.json` contains only `auth_mode` and `OPENAI_API_KEY`. See [Agent Model Configuration](AGENT_MODELS.md#destructive-rebuild-recovery) for the exact output and eligibility contract.

Immediately before writing, the manager verifies that files still match the approved revision. `PREVIEW_STALE` means a target changed; no write begins and a fresh preview is required. Existing files are backed up before replacement. The desktop submits exactly one Agent while retaining transactional safety across that Agent's complete file set: failure causes already changed files to be rolled back, while diagnostic backups are retained. If rollback cannot be proven, further Agent writes fail closed.

Backups remain beside the original configuration and may contain an old API key. They are sensitive recovery artifacts: protect, retain, or remove them with the same care as the original Agent file. Preview shows only planned sibling backup patterns; a successful result shows actual paths after verified byte-for-byte backups are created. Neither displays backup contents, and a failed operation may show only its error. Never manually restore while a transaction journal or unresolved recovery exists; contact the maintainer because changing a target can prevent recovery from proving its identity. After recovery is resolved, stop the owning Agent, preserve current files, verify that the original path and parent retain their expected current-user, non-link identity, then use a private same-directory temporary file and atomic replacement. For Codex, restore only files that existed before the transaction and remove a newly created companion only when the reviewed operation proves its prior absence; otherwise contact the maintainer.

Detection's `configured` state means only that local managed fields are structurally complete and internally consistent. It does not prove the selected models are currently authorized. Entering the panel, manual refresh, and throttled native-focus refresh use the saved global key to obtain a fresh catalog; there is no polling or background Agent-file rewrite. Catalog/auth/validation failures, a disappeared model, drift without approval, or invalid ownership state fail closed with no static/cached fallback or partial write. See [Agent Model Configuration](AGENT_MODELS.md) for the service contract, canonical schema, omission, migration, and ownership rules.

For Claude, canonical configuration stores the authenticated base model ID and optional exact `context: "1m"` separately. Enabled Fable renders `ANTHROPIC_DEFAULT_FABLE_MODEL` and an optional `ANTHROPIC_DEFAULT_FABLE_MODEL_NAME`; absent Fable renders and claims neither. Preview shows collisions before an enabled Fable claims an existing unowned value, and disabling Fable removes only stale paths proven previously manager-owned while preserving never-owned manual keys. The manager appends `[1m]` only while rendering Claude's model environment values; it does not infer 1M support or write `CLAUDE_CODE_DISABLE_1M_CONTEXT`. A runtime rejection does not cause fallback or rewrite. The Fable alias requires Claude Code 2.1.170 or newer. Separately, numeric custom-model context overrides work directly for unknown model names on Claude Code 2.1.193 or newer; older versions may ignore them. Preset discovery itself writes no Agent file or manager transaction state, and preset data is stored only as key-free model state in the desktop flow.

## API-key boundary and limitations

The API Keys page saves, replaces, or deletes one global API key in the desktop credential store; the webview can read only its summary, never the plaintext value. The Agents overview neither reads nor validates that key. Rust loads it on demand only after a card action for `agent.models`, then loads the current saved value again immediately before `agent.write`. The desktop `ModelFlow` contains Agent, catalog, and preview-mode state but no API key. Secret-bearing calls are never automatically replayed after timeout, malformed response, manager restart, or uncertain delivery. Outside the credential store and Agent files or approved backups, the key is not intentionally placed in desktop or manager persistent state, process arguments, environment variables, logs, diagnostics, model config, catalog/revision tokens, preview responses, or write responses.

The target Agent configuration must persist the key where that Agent requires it until that Agent is cleaned up. Per-Agent cleanup removes the managed Agent-file credential but deliberately retains the desktop global key. User-approved recovery and cleanup backups may also persist an older key. Rust holds each on-demand use in zeroizing memory, but clearing application references is best effort and is not a guarantee of forensic erasure from process or operating-system memory.

`MTLS_ROUTER_OPENAI_API_KEY` has been removed and no longer supplies a key. For exact noninteractive manager automation, see [stdin manager automation](#stdin-manager-automation).

## Stdin manager automation

Automation must invoke the receipt-verified installed `mtls-router-manager serve`, require `manager.info` protocol `4`, call `agent.models` with the transient key, construct canonical model config, call key-free `agent.render` or `agent.preview`, and finally call `agent.write` with the revision token, explicit approvals, and transient key. The key must not be an argument, exported environment variable, model-config value, log value, or temporary request file. Catalog tokens are intentionally verifiable across one-shot manager processes. See the exact [protocol v4 automation contract](AGENT_MODELS.md#protocol-v4-automation).

## Credential model

Each production package is bound to one service environment. The router sidecar contains a shared client certificate, shared private key, upstream CA, and default upstream URL. A user who can obtain the package can extract those embedded values; packaging and the desktop UI cannot prevent this. Distribute packages only to trusted internal users.

Revocation or rotation requires a replacement release built with new credential material, distribution of the complete replacement package, and server-side rejection of the old credential. There is no runtime certificate import, profile switch, or independent sidecar update. A stable whole-package desktop update can distribute the replacement application and matched sidecars after user confirmation; CLI installations still require the existing CLI distribution and setup process.

The local listener is plain HTTP on trusted localhost. Do not expose the management endpoints or listener publicly.

## Uninstall

- Windows: quit the application, then uninstall it from Windows Settings. The production installer must remove the desktop application's current-user launch-at-login registration during uninstall.
- macOS and Linux: open Settings, select **Prepare for uninstall**, and confirm. Wait for the application to remove current-user launch-at-login and exit. Only then delete the macOS application or Linux AppImage.

No uninstall path restores, deletes, or rewrites Agent configurations, sensitive backups, router logs, application state, or diagnostic state. Remove any of those separately only after reviewing what must be retained for recovery or diagnosis.
